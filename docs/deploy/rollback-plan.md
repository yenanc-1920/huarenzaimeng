# 回滚方案

> 目标：生产故障时 5 分钟内完成回滚，恢复上一稳定版本。

---

## 1. 回滚触发条件

满足以下任一条件即触发回滚评估：

| 指标 | 阈值 | 观察窗口 |
|------|------|----------|
| HTTP 5xx 错误率 | > 5% | 连续 3 分钟 |
| P99 响应延迟 | > 5s | 连续 5 分钟 |
| 充值成功率 | < 90% | 连续 10 分钟 |
| OOM / 容器重启 | ≥ 2 次 | 10 分钟内 |
| 健康检查失败 | 连续 3 次 | — |

## 2. 回滚策略

### 2.1 应用回滚（云托管版本切换）

微信云托管保留最近 5 个部署版本。

**操作步骤：**

1. 登录云托管控制台 → 服务管理 → 版本管理
2. 选择上一稳定版本（tag 格式：`{commit-sha}` 或 `{branch-name}`）
3. 点击「回滚到此版本」→ 确认
4. 等待实例滚动更新完成（约 60-90 秒）
5. 验证 `/actuator/health` 返回 UP

**命令行（tcb CLI，如已配置）：**

```bash
tcb service rollback --env-id prod-d3g9ntdmsdf9d7877 \
  --service-name huarenzaimeng-server \
  --version <previous-version-id>
```

### 2.2 数据库回滚

**V1 策略：Forward-fix（只进不退）**

- Flyway 迁移脚本只增不改不删
- 如迁移引入问题，编写新的修复迁移（V{n+1}__fix_xxx.sql）
- 云托管版本回滚后，旧代码需兼容新 schema（向后兼容原则）

**紧急情况（数据损坏）：**

1. 停止写入：云托管缩容至 0 实例
2. 从腾讯云自动备份恢复（保留 7 天，RPO ≤ 5 分钟）
3. 恢复后扩容至正常实例数
4. 验证数据完整性

### 2.3 配置回滚

- 环境变量变更通过云托管控制台修改，支持即时生效
- 如配置变更导致故障，恢复上一版本配置值
- 所有配置变更记录在 `docs/deploy/config-changelog.md`

## 3. 紧急回滚流程（< 5 分钟）

```
T+0:00  发现异常（告警/人工）
T+0:30  确认回滚（DevOps 或值班人员决策）
T+1:00  云托管控制台 → 版本回滚
T+2:30  实例滚动更新完成
T+3:00  健康检查通过
T+4:00  验证核心链路（一笔测试充值）
T+5:00  回滚完成，通知团队
```

## 4. 回滚后事项

- [ ] 记录故障时间线（发现 → 决策 → 回滚 → 恢复）
- [ ] 创建 hotfix 分支修复根因
- [ ] 修复后走正常发布流程重新上线
- [ ] 更新风险矩阵（如需）

## 5. 版本保留策略

| 项目 | 策略 |
|------|------|
| 云托管版本 | 保留最近 5 个 |
| 镜像仓库 tag | 保留最近 10 个 + 所有 master tag |
| 数据库备份 | 腾讯云自动备份，保留 7 天 |
| Flyway 迁移记录 | 永久保留（flyway_schema_history 表） |

## 6. 演练计划

- 上线前（Sprint 5 T-5.6）：完整回滚演练 1 次
- 上线后：每月 1 次回滚演练（非高峰时段）
- 演练记录存入 `docs/deploy/drill-records/`
